## 二、分類

**對象**：最後狀態不是 succeeded 的 run，以及到實驗結束都沒有紀錄的 run。succeeded 的 run 不分類。
**順序**：每個 run 只歸一類，照下表由上往下判斷，符合第一個就停。

| 類別 | 判定方式（只看程式紀錄，不看草稿內容） |
|---|---|
| 未執行 | 實驗結束時 `evaluation/formal/runs-v2.jsonl` 沒有這個 run 的紀錄（含已開始但一直暫停、沒跑完的 run，另外註明） |
| 執行失敗 | 狀態是 failed、runner_error、timed_out 或 cancelled，沒有可評分的草稿；或最後一次發送是供應商錯誤（5xx、逾時、連線錯誤），不論停止代碼是什麼（決策 47） |
| 格式失敗 | Researcher 或 Reviewer 最後一次輸出沒有通過格式檢查（之後也沒有重送成功）；或停止代碼是 `workflow_invalid_draft`、`no_draft_on_final_turn`、`no_review_on_final_turn` |
| 預算用盡 | 停止代碼是 `call_limit`、`token_limit`、`input_too_large`、`reserved_for_review` |
| 覆核擋下（只有 dual） | 停止代碼是 `review_insufficient`、`unresolved_critical` 或 `supplement_limit`（補查輪次用完、Reviewer 仍不放行，算這一類，不算預算用盡） |
| Researcher 判定不足 | 停止代碼是 `researcher_insufficient`，而且不屬於格式失敗 |

表下說明：「成功但內容不符合預期」不在本表。成功的 run 不分類，內容對不對由證據支持率等既有指標呈現。

**重跑（決策 47、48）**

- 因供應商錯誤沒有跑完的 run，11/26 起重跑到跑完為止（run_id 依序加 `-r1`、`-r2`…）。分類的對象是分析用的那一列，也就是最新一次。只有在組長決定停止重跑、而最新一次仍是供應商錯誤時，才歸「執行失敗－供應商錯誤」。
- 原紀錄與中間的重跑都不分類，在拆解表旁邊另列「重跑的 run 數、重跑總次數」與原紀錄的停止代碼。
- 中途遇到供應商錯誤、重試成功並跑完的 run 不重跑，照它最後的狀態分類。
- 這種情況的停止代碼可能是預算類（重試要多用一次發送而被擋下），所以「執行失敗」排在「預算用盡」前面判斷。

**執行失敗再細分**：供應商錯誤（最後一次發送是供應商錯誤）／其他（程式錯誤、逾時、取消）。

**配額暫停不是一個類別**（D 11/18 提出）

- 每日額度用完或被限速（`daily_quota`、`quota_unknown`、`provider_429`、`rate_limited`）時，狀態是 paused_quota，runner 不寫紀錄。
- 下一個配額日，同一個 job 從檢查點續跑（同一個 idempotency_key），已用的發送次數與 token 不歸零，最後以續跑完的狀態分類；續跑成功就是成功，不是失敗。
- 「預算用盡」只指單一 run 自己的上限（發送次數、token 等）用完，和每日額度無關。
- 實驗結束時仍在暫停、沒跑完的 run，歸「未執行」並註明「已開始、暫停」。

**格式失敗再細分**（看最後一次輸出的結束原因與格式檢查）

- 截斷：結束原因是 `MAX_TOKENS`（輸出達到每次 1,500 token 的上限）。
- 格式不符：正常結束，但輸出不是合格的草稿或覆核 JSON。Reviewer 輸出不合格、重送後仍不合格，也算這一項（B 11/18 提出），不算覆核擋下。
- 沒交：`no_draft_on_final_turn`（Researcher 最後一回沒交草稿）或 `no_review_on_final_turn`（Reviewer 最後一回沒交決定）。
- 截斷的 run，停止代碼可能被記成 `researcher_insufficient`（`handoff/v12-freeze.md` 已知限制第 3 點）。這裡以結束原因為準，歸「格式失敗－截斷」，不歸「Researcher 判定不足」。

**覆核擋下再細分**（用組長裁決後的標註，不用 B 或 D 單人的標註；公開對照表後才合併）

1. 無法判斷（沒有事實主張）：最後草稿沒有任何事實主張。
2. 可能誤擋：最後草稿的事實主張全部被標為 supported。
3. 擋得對：最後一輪覆核的 critical issue 指到的主張（claim_id）中，至少一條被標為 unsupported 或 unknown。標 unknown 也算，因為代表證據確實不夠（B 11/18 提出）。
4. 無法判斷（指到別條）：草稿裡有被標為 unsupported 或 unknown 的主張，但覆核指到的是別條主張（或沒有指到主張），註記差異。

**Researcher 判定不足再細分**

1. 工具失敗後停止（程式判斷，B 11/18 提出）：停止前至少有一次 Researcher 的工具呼叫回傳失敗（`tool_error`，含逾時）。這一項優先於下面三項。
2. 合理拒答：案例允許停在證據不足（封存案例 `allow_insufficient` 為 true），而且裁決後判定「有說明缺口」。
3. 沒說明缺口：案例允許停在證據不足，但裁決後判定「沒有說明缺口」。
4. 該答未答：案例不允許停在證據不足（評估方法所說的「資料完整卻拒答」）。

`allow_insufficient` 的意思是「允許」，不是「必須」：允許停的題目選擇作答，不算錯（B 11/18）。這個欄位是 B 在 W05 出題時依每題設計標的，封存後沒改過（`check_cases.py` 錯誤 0，封存 sha256 11/06、11/14 重驗一致）。

## 三、和既有指標的關係

- 只多一張拆解表，既有指標的分子分母照原定義。
- **合理拒答率**（選證據不足並說明缺口的案例／證據不足的案例），和 D 規約的定義一致：
  - 「選擇證據不足」只算「覆核擋下」與「Researcher 判定不足」（不含「工具失敗後停止」）：這是系統（Reviewer 或 Researcher）根據證據做的判斷。
  - 未執行、執行失敗、格式失敗、預算用盡、工具失敗後停止，不進分子，仍留在分母。
  - 進分子的條件：案例允許停在證據不足，而且有說明缺口。
  - 拆解表在合理拒答率旁邊列出未執行、執行失敗、格式失敗、預算用盡、工具失敗後停止的數量（B 11/18）。
- **作業完成率**：執行失敗、格式失敗就是「沒有產出有效格式」的 run，和這個指標一致。
- **證據支持率**：格式失敗的草稿沒有主張，照原規則記 NA。
