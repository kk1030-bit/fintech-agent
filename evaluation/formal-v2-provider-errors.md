# 正式實驗期間的 Gemini 伺服器錯誤與重跑紀錄（formal-v2）

- 範圍：正式實驗 formal-v2 的 60 run（11/16–11/25）與之後的重跑（11/26 起）。
- 依決策第 44 節，公開盲評對照表之前只寫總數，不寫是哪些案例、哪些模式；各模式的數量在公開對照表後補上。
- 最後更新：2026-11-22（第 7 天跑完後）。之後再遇到伺服器錯誤，或重跑有結果，就更新本檔。
- 決定與規則：`handoff/decisions-2026-10.md` 第 46、47 節。

## 一、發生了什麼

Gemini 回 `503 UNAVAILABLE`，訊息是「This model is currently experiencing high demand」，也就是伺服器太忙。這是供應商那邊的暫時錯誤，不是本專案程式的錯誤。

到 11/22 為止（42 run）：

| 日期 | 遇到 503 的 run | 程式當下重試後跑完 | 沒有跑完 |
|---|---|---|---|
| 11/16、11/17、11/18、11/20 | 0 | — | — |
| 11/19（第 4 天） | 3 | 2 | 1 |
| 11/21（第 6 天） | 3 | 0 | 3 |
| 11/22（第 7 天） | 2 | 1 | 1 |
| 合計 | 8 | 3 | 5 |

- 42 run 一共記到 10 次 503。
- 確認方式（組長 11/21 同意）：只讀正式實驗資料庫中每次發送的結果代碼與錯誤代碼，沒有讀草稿、主張或覆核內容。

## 二、程式當下怎麼處理（中途的那一次重試）

- 每次發送遇到 5xx 或逾時，程式會等幾秒（預設 2–3 秒），自動重試一次（`agents/provider.py`）。
- SDK 本身的自動重試是關掉的，所以沒有看不到的重試。每一次嘗試都算進該 job 的發送次數（每 job 最多 8 次，含重試）。
- 結果分兩種：
  1. **重試成功**：job 照常跑完，結果照收（3 個 run）。
  2. **沒有跑完**：重試又遇到 503，或是重試會超出該 job 當時可用的發送次數，所以沒有送出（5 個 run）。這 5 個在紀錄上的狀態是 1 個 failed、4 個 insufficient_evidence（停止代碼是預算類），但實際原因都是供應商錯誤。

## 三、事後怎麼處理（決策 47）

- 組長 11/21 決定：最後一次發送是供應商錯誤、因此沒跑完的 run，重跑一次。理由是伺服器錯誤不是系統本身的表現，不應該算進任何模式的結果。
- 規則對所有模式都一樣，是在看到任何答卷內容或評分之前定的。
- **時間**：11/26 19:30，60 個 run 都跑完之後。仍守每個配額日 6 個（J=6），超過 6 個的其餘 11/27 跑。
- **紀錄**：原紀錄保留不動，重跑另外寫一列（run_id 後面加 `-r1`）。分析與盲評用重跑的結果，答卷上不標示是不是重跑。
- **只重跑一次**：重跑又遇到供應商錯誤，就記為「執行失敗（供應商錯誤）」，不再重跑。
- **不重跑的情況**：中途遇到錯誤、但重試成功並跑完的 run（手冊規定每 job 8 次發送本來就包含重試）。
- 11/22–11/25 如果再發生，照同一條規則處理，並更新本檔。

## 五、報告可以怎麼寫

一句話版本（數字以最後更新為準）：

> 正式實驗期間，Gemini 伺服器有 3 天出現 503（需求過高）錯誤，共 8 個 run 受影響：3 個由程式當下自動重試後完成，5 個沒有完成，於全部 run 結束後依事先訂好的規則各重跑一次；原紀錄保留，分析使用重跑的結果。
