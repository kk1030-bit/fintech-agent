# 正式實驗期間的 Gemini 伺服器錯誤與重跑紀錄（formal-v2）

- 範圍：正式實驗 formal-v2 的 60 run（11/16–11/25）與之後的重跑（11/26 起）。
- 依決策第 44 節，公開盲評對照表之前只寫總數，不寫是哪些案例、哪些模式；各模式的數量在公開對照表後補上。
- 最後更新：2026-11-25（第 10 天跑完，計畫中的 60 run 全部跑完）。之後再遇到伺服器錯誤，或重跑有結果，就更新本檔。
- 決定與規則：`handoff/decisions-2026-10.md` 第 46–48 節。

## 一、發生了什麼

Gemini 回 `503 UNAVAILABLE`，訊息是「This model is currently experiencing high demand」，也就是伺服器太忙。這是供應商那邊的暫時錯誤，不是本專案程式的錯誤。

11/24 另有 1 次 `504 DEADLINE_EXCEEDED`：Gemini 伺服器沒有在時限內完成回應（時限 45 秒由程式送給伺服器；平常一次發送只要幾秒）。程式當下用同樣的內容重試，馬上就成功了，所以不是輸入太長之類的問題，同樣算供應商的暫時錯誤（決策 47 的規則本來就包含 5xx）。程式自己等到逾時的情況會記成 408，和這次不同。

60 run 全部跑完（11/16–11/25）：

| 日期 | 遇到伺服器錯誤的 run | 程式當下重試後跑完 | 沒有跑完 |
|---|---|---|---|
| 11/16、11/17、11/18、11/20、11/23 | 0 | — | — |
| 11/19（第 4 天） | 3 | 2 | 1 |
| 11/21（第 6 天） | 3 | 0 | 3 |
| 11/22（第 7 天） | 2 | 1 | 1 |
| 11/24（第 9 天） | 3 | 2 | 1 |
| 11/25（第 10 天） | 1 | 0 | 1 |
| 合計 | 12 | 5 | 7 |

- 60 run 共 243 次發送，其中 14 次是伺服器錯誤：503 有 13 次、504 有 1 次。沒有其他錯誤代碼（包括 429 額度錯誤）。
- 確認方式（組長 11/21 同意）：只讀正式實驗資料庫中每次發送的結果代碼與錯誤代碼，沒有讀草稿、主張或覆核內容。

## 二、程式當下怎麼處理（中途的那一次重試）

- 每次發送遇到 5xx 或逾時，程式會等幾秒（預設 2–3 秒），自動重試一次（`agents/provider.py`）。
- SDK 本身的自動重試是關掉的，所以沒有看不到的重試。每一次嘗試都算進該 job 的發送次數（每 job 最多 8 次，含重試）。
- 結果分兩種：
  1. **重試成功**：job 照常跑完，結果照收（5 個 run）。
  2. **沒有跑完**：重試又遇到 503，或是重試會超出該 job 當時可用的發送次數，所以沒有送出（7 個 run）。這 7 個在紀錄上的狀態是 1 個 failed、6 個 insufficient_evidence（停止代碼是預算類），但實際原因都是供應商錯誤。

## 三、事後怎麼處理（決策 47、48）

- 組長 11/21 決定：因供應商錯誤沒跑完的 run 要重跑；11/22 改為**重跑到跑完為止**（組員都同意）。理由是伺服器錯誤不是系統本身的表現，不該是 run 停下來的理由，也不應該算進任何模式的結果。
- 被鎖定的 Agent 程式不修改（不解凍）：已跑的 run 和所有重跑都是同一個版本。
- 規則對所有模式都一樣，是在看到任何答卷內容或評分之前定的。
- **時間**：11/26 19:30，60 個 run 都跑完之後。重跑日的 job 數上限放寬到 50，每日 80% 額度（400 次發送）的上限不變；每個 job 之間等 1 分鐘。
- **紀錄**：原紀錄保留不動，每一次重跑都另外寫一列（run_id 依序加 `-r1`、`-r2`…）。分析與盲評用最新一次的結果，答卷上不標示是不是重跑。
- **重跑到跑完為止**：重跑又遇到供應商錯誤，就再重跑一次；某一次因為供應商以外的原因結束（成功、證據不足、其他失敗都算）就停。當天配額用完還沒跑完的，下一個配額日再續。
- **不重跑的情況**：中途遇到錯誤、但重試成功並跑完的 run（手冊規定每 job 8 次發送本來就包含重試）。
- 計畫中的 60 run 已在 11/25 全部跑完，要重跑的最後是 7 個。

## 五、報告可以怎麼寫

一句話版本（數字以最後更新為準）：

> 正式實驗期間，Gemini 伺服器有 5 天出現暫時性錯誤（503 需求過高，另有 1 次 504 逾時），共 12 個 run 受影響：5 個由程式當下自動重試後完成，7 個沒有完成，於全部 run 結束後依事先訂好的規則重跑到完成為止；原紀錄保留，分析使用最後一次的結果。

- 各模式受影響的數量，以及重試會占用發送次數對各模式的影響，在公開對照表後補上。
